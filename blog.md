# How We Taught an AI to Think Like a Compiler (And Then Break Itself to Get Better)

So the whole thing starts with a pretty simple observation. These days you do not need to know how to write a single line of code to build something real. You just need an idea and the right tools, and the LLMs do the rest. We thought about exactly this and then started pulling on that thread a little more. The recent boom of LLMs has changed literally every person's life, not just people in tech, not just developers, just everyone. And then the next obvious thought was that this thing is not going anywhere anytime soon. So if LLMs are here to stay, and all of them running on massive datacentres packed with GPUs eating up electricity and compute like it is free, then finding a way to make even that underlying system five percent more efficient would genuinely matter. That is the kind of problem worth spending a hackathon on.

So we started digging. And what we found is that compilers have been getting optimized for decades. Almost every part of the compilation pipeline has had smart people throwing research at it for years. Almost every part. The one place we kept finding a weird gap was IR optimization, Intermediate Representation optimization, the step where the compiler takes a mid level version of your code and tries to make it leaner before turning it into machine instructions. And when we read more about it, it hit us almost immediately that this problem was tailor made for a self improving algorithm using reinforcement learning, which was exactly the area we had been most excited about since round one. So without a second thought we locked it in.

The project had three parts. The compiler environment and optimization logic, the RL pipeline connecting everything to Hugging Face and Unsloth so the agent could actually train, and the data generation and evaluation side where the agent teaches itself, generates its own training data, sets its own difficulty, and judges its own answers. Three people, three very different problems, one pretty wild idea.

The first thing we had to figure out was how to represent the compiler state in a way an RL agent could actually learn from. We designed a custom Three Address Code intermediate representation where every instruction was a clean structured dictionary with an operation, a destination, and source values. The real magic was in the cycle costs we assigned to each operation. NOPs cost nothing, addition and subtraction cost one cycle, multiplication costs three, load and store cost four, division costs five. These were mapped to real CPU latencies, not made up numbers. And this mattered enormously because without real costs the model would just learn to delete lines of code to reduce the cycle count, which is cheating and also completely useless. By making different operations worth different amounts the agent was forced to understand the actual value of what it was doing. We also made sure it could not just delete the entire program and call it a day, store operations were treated as non negotiable observable outputs and any pass that changed the final memory state triggered a minus one thousand penalty. Correctness was never optional.

On the forward optimization side we built constant folding with deep propagation, peephole optimization for algebraic identities like multiplying by one or adding zero, and dead code elimination that traces backwards from store operations and wipes out any calculation that never actually contributes to the output. These three chained together became the core forward loop and they are genuinely powerful on their own.

But here is the part we are most proud of and honestly the thing that changed the entire direction of the project. A pure forward pass system mathematically traps the agent in a local minimum. It can only ever reduce the cycle count, so it grabs the first decent solution it finds and gets stuck there forever. We came across a paper called Beyond Phase Ordering and what it proposed stopped us in our tracks. What if you deliberately take the IR to the worst possible state it could be in, the complete opposite of optimized, and then climb back from there? Optimizing the original code directly might get you twenty percent efficiency. But taking it to the bottom first and then optimizing gets you forty percent. The actual global maximum. Not a nearby peak, the real top.

The analogy that made it click was this. Imagine you are standing at a decent height and you want to reach the absolute highest peak. Right in front of you there is a short peak and if you just climb that you will think you have done well. But if you first walk into the valley and go lower than where you started, suddenly you can see the whole landscape and you can finally see where the real highest peak is. That valley is not a setback, it is the only way to see the full picture. This is exactly what the reverse passes do. We built an expand constant pass that splits a constant into two operations, costing one extra cycle deliberately, and a duplicate computation pass that creates a redundant copy of an operation. Both of these look like terrible moves in isolation. And they are. That is the whole point. They break apart rigid structures so that the forward passes can re-fold the math in a way that was mathematically impossible before. You have to make it worse to find out how much better it can actually get. When Sanyam Sir said in the opening ceremony that doing trivial work will not get anyone anywhere, this is the moment we thought about. Because this is not trivial. Nobody is doing this.

We also built a five level curriculum because you cannot throw a hard problem at an RL agent on day one. Level one and two were simple programs to teach the basic constant fold into dead code elimination loop. Level four introduced fan out topology where a single load feeds eight or more downstream calculations, teaching the agent that one well placed pass can cascade through a massive graph. Level five was thirty to forty five instructions, heavily biased toward expensive multiply and divide operations, with over seventy percent of the arithmetic containing hidden zeros and ones as peephole bait. Average starting cost eighty four cycles, average after optimization twenty six cycles. That gap is where the agent learned to hunt.

For evaluation we built our own equivalent of a minus O3 compiler flag, a fixed point loop that keeps applying the forward passes until the cycle count stops changing, tested on a hundred program held out set with completely separate random seeds to guarantee zero data leakage. That baseline hit sixty four point three percent aggregate cycle reduction. That was the bar.

Making all of this work as a living system was its own battle. Raw compiler output was too noisy for the model to reason over, so we built a Translator layer that converted the low level state into clean pseudo assembly representations that matched the model's pre-trained intuition. We wrapped the compiler engine into a standard Gym style API with reset, step, and state methods so the model had a proper structured environment. The model would read the state, output a JSON array of optimization passes, and that array would go straight into the step function.

Except LLMs are very polite. Instead of just giving the array the model would respond with something like certainly, based on my analysis of the current state I believe the following optimizations would be beneficial, and then somewhere in that paragraph was the actual answer. So we built a regex based fallback parser that ignored all the conversational warmth, found the brackets, pulled the array out, and passed it to the execution engine. Small fix, massive stability improvement.

For the RL training itself we used GRPO, Group Relative Policy Optimization, through Hugging Face TRL. Instead of judging one attempt at a time the model generates multiple candidate strategies and learns by comparing which ones performed better relative to each other. It learns by watching its own questionable decisions play out side by side. We used Unsloth for efficient fine tuning with four bit precision to get the full training loop running on a single GPU without an out of memory disaster. And we learned very painfully that torch, transformers, unsloth, and flash attention have extremely strong opinions about installation order. One careless pip install everything command and the environment does not set up, it stages a full rebellion. Careful pinning, intentional kernel restarts at every stage, that is the only way through.

When you zoom out and look at what we actually built, a self improving agent trained on twenty five thousand programs it generated itself, optimizing over four hundred thousand iterations, learning not just how to make code better but learning when to first make it worse so it can find the real best, it is genuinely kind of wild. The heuristics compilers have been using for thirty to forty years were written by humans who could think about three or four things at a time. We built something that considers all twenty three optimization passes at once, understands their interactions, and finds the combinations that no human rule ever would. And the reverse pass is what made that possible. That is the thing we are most proud of walking out of here.
